# LiveAgent 面试问答预案（13 个高频追问）

> 2026-08-02 起草，配合 `liveagent-architecture-positioning.md` 使用。
> 每条：面试官意图 → 一句话回答 → 展开（含证据/文件）→ 可能追问。
> 原则：如实回答，主动亮出边界（面试官一眼能看穿的洞，先自己说出来并给理由）。

## Q1. 为什么播前是 Workflow，播中才是 Agent？

- **意图**：考察对"何时该用 Agent"的架构判断，而非"会不会用 Agent"。
- **一句话**：流程确定用 Workflow，有模型决策点才用 bounded Agent——不是所有环节都适合 Agent。
- **展开**：播前排品/手卡是确定性流程（输入明确、步骤固定、无模型决策点），用 LangGraph
  Workflow + RulesPlanner 保证稳定可复现；播中弹幕/告警需要理解语境、权衡冲突，才有
  模型决策点，用 bounded Agent。README 开发说明也明确写了这条边界。
- **追问"为什么不全部 Agent 化"**：Agent 的收益在决策点，成本是延迟、成本与不可审计性；
  确定性部分用规则是刻意的架构克制。

## Q2. 为什么 Agent loop 必须有上限？

- **意图**：考察对 Agent 失控风险（成本/延迟/不可审计）的认识。
- **一句话**：上限 + 预算 + 账本把"自主性"变成"受治理的有限自主"。
- **展开**：`SpecialistProfile` 冻结 `max_model_calls` / `max_skill_calls` /
  `max_total_tokens` / `deadline_seconds` / `max_case_cost_cny`；
  `BoundedSpecialistRunner.run()` 在预算内循环，预算先预留后结算，超限 fail-closed。
- **追问"上限会不会限制能力"**：会，但运营产品要的是可预测行为；能力不足靠调参/换模型，
  不靠放开循环上限。

## Q3. Analyst 和 Planner 为什么拆成两个 Agent？

- **意图**：考察多 Agent 分工的合理性，以及是否理解"拆"的代价。
- **一句话**：分析（发生了什么）与决策（怎么办）职责分离，各自有独立 schema 契约、可单独验证与升级。
- **展开**：`evidence_analyst` 产出结构化冲突分析（ConflictAnalysis），`decision_planner`
  基于分析产出方案（Proposal）；每阶段输出 schema 冻结（`result_schema_hash`）、证据以
  身份引用注入，阶段间可拦截。这是受控顺序编排——不是自主辩论（见定位文档 §4）。
- **追问"为什么不辩论"**：运营高风险场景要可审计、可拦截；自主辩论提高自主性的同时
  提高不可审计性与不可预测性，与场景目标相反。

## Q4. Skill、Tool、普通函数的边界是什么？

- **意图**：考察工具抽象与治理设计。
- **一句话**：模型能调用的必须是受治理的 Skill；Tool 是可见性/权限层；普通函数不允许
  被 Agent 绕过治理直接调用。
- **展开**：Skill = 能力单元（`skill_runtime/catalog.py` 25+ 项），带 lifecycle ×
  risk_level × gate_decision 三重治理 + attempt_store 审计；Tool = trust_score 可见性
  mask（`memory/tool_mask_policy.py`）；函数 = 无模型参与的确定性实现。
- **追问"为什么 Skill 要版本化"**：`skill_versions` 随 profile 冻结，保证同一契约下
  行为可复现，评估结果不被"悄悄改的 skill"污染。

## Q5. 模型输出如何防止伪造证据和未授权工具调用？

- **意图**：考察对 LLM 幻觉/越权的防御工程。
- **一句话**：输出 schema 冻结 + 证据身份绑定 + 动作归属校验 + 预算/权限双重门禁。
- **展开**：模型只能产出 schema 内输出（`additionalProperties: false`）；证据只以
  `EvidenceRef` 身份注入与回传（模型拿不到证据正文）；runner 校验动作引用的证据必须
  属于任务初始证据集（归属校验）；Skill 调用受 `allowed_skill_ids` 白名单 + 预算预留约束。
- **追问"模型传一个不存在的 evidence_id 呢"**：`_collect_result_evidence_ids` +
  归属校验会拒收未授权引用，run 标记失败入账。

## Q6. 为什么生产默认是 DETERMINISTIC_ONLY？

- **意图**：考察安全设计优先级与降级思维。
- **一句话**：经营动作高风险，确定性规则先保底，模型建议必须过门槛再过人审。
- **展开**：售罄保护等确定性逻辑先执行，仅高冲突证据满足门槛时顺序运行双 Agent 产出
  建议，人审批准才执行；模型不可用时规则引擎安全降级，业务仍可运行。LLM 自动路由
  **未放开**（诚实边界），这本身就是受控验证的一部分。

## Q7. 8 PASS / 4 FAILED 如何解释？

- **意图**：考察对评估证据的诚实性与对防刷分的理解。
- **一句话**：12 个真实模型 run 的终态如实保留在 append-only 账本——4 个 FAILED 是
  开发期失败 run，防刷分设计禁止重跑洗绿。
- **展开**：账本 271 receipts / 6.604131 CNY；失败终态不可重跑是刻意的审计设计——
  全绿的账本反而可疑；"7 指标 12/12"指每个 PASS run 内部，不是 12 个 run 全过。
- **追问"为什么不重跑到全绿"**：预算逐次批准 + 防刷分 + 诚实审计；修复后重新跑产生
  新 run，历史 FAILED 永远保留。

## Q8. 为什么 V9 不能叫原始 V5 PASS？

- **意图**：考察契约意识与历史审计严谨性。
- **一句话**：V5 契约（单渠道、零重试、预算 ≤1.0）与实际执行（渠道链、受控重试、
  6.60 CNY）存在经批准的偏差，所以 V9 是新的回溯评价身份，不追认 V5。
- **展开**：v2 历史执行契约冻结（digest `1aa9ca6f...`）、v3 纯回溯评价契约闭合
  （`75319a4a...`）、Phase 17 独立执行契约——三个契约三个身份，互不覆盖；V5 保持
  "未通过、未恢复"的历史状态。
- **追问"偏差经过批准吗"**：每一次预算/渠道/重试变更都经用户逐次批准（对话转录），
  批准链记录在 `phase-16-v9-contract-approval-record.md`。

## Q9. 失败调用和 retry 是否会污染评分？

- **意图**：考察评估管线的防污染设计。
- **一句话**：append-only 账本按 attempt 记账，transport 重试与逻辑 stage 分离计数，
  失败如实入账，不重跑不洗绿。
- **展开**：三计数分离（logical_stage / transport_attempt / receipt）；retry 有受控
  语义（TRANSPORT/5xx 可重试、429 换端不重试、窗口/次数上限）；历史 FAILED run 终态
  保留；V9 receipt 必须带实际端点与尝试次数才算完整回执。

## Q10. 记忆是检索，还是模型真的在线学习？

- **意图**：考察是否诚实区分"记忆管线"与"学习"。
- **一句话**：是受治理的检索与候选存储管线，不是模型自主学习——这是刻意先做的安全版本。
- **展开**：`stage_memory_candidates` / `retrieve_anchor_memory` 带证据约束、脱敏、
  幂等键、SOFT_GATE 门禁、trust_score；先证明记忆过程可审计可回滚，再谈学习能力
  （架构定位文档 §7）。
- **追问"为什么不直接做学习"**：无治理的学习在审计/回滚上不可控；对运营系统，先安全后能力。

## Q11. 没有真实业务 KPI，如何证明系统有价值？

- **意图**：考察是否会把"工程验证"包装成"业务证明"。
- **一句话**：不包装——工程层证据链完整（V9 qualification + holdout 预声明阈值），
  业务层如实声明"未部署、无 KPI"。
- **展开**：价值主张分两层：工程层（受控验证方法学：预声明阈值、防泄漏、防调参、
  append-only）已被验证；业务层（转化率/损失率改善）是生产部署后的阶段，范围外。
- **追问"那它有什么用"**：作为求职项目，展示的是评估纪律与工程完整度；作为产品原型，
  是生产前候选系统，落地路径已在计划中（只读建议 → 人审 Skill → 有限自动化）。

## Q12. Docker Compose 单节点、默认凭据、未鉴权端点能否进入生产？

- **意图**：考察对生产运维差距的清醒认识。
- **一句话**：不能——这是明确的开发环境特征，生产部署范围外、未做生产就绪声明。
- **展开**：单节点 compose、默认凭据、README 部分端点未鉴权，都是开发/演示环境的
  已知事实（README「诚实边界」已声明）；生产化（HA/密钥管理/鉴权/限流/监控/灾备）
  是"生产化剩余工作"，未完成即不声明生产就绪。

## Q13. 如果模型完全不可用，业务是否仍能安全运行？

- **意图**：考察降级设计与容错。
- **一句话**：能——DETERMINISTIC_ONLY 默认路由下规则引擎兜底，模型不可用自动降级。
- **展开**：确定性售罄保护先于模型执行；模型调用失败有受控重试/渠道链/降级路径；
  demo 与 CI 全程 `PHASE15_REAL_MODEL=0` 可跑，证明无模型时核心链路仍闭环。

## 使用说明

- 预案是"立场 + 证据"，不是背诵稿；面试时按真实数据回答（数字以账本/文档为准）。
- 所有边界词（范围外/未声明/不包装）**必须如实使用**——编造业务证据是唯一不可逆的错误。
- 配套文档：`liveagent-architecture-positioning.md`（架构）、README「验证证据链/诚实边界」节
  （证据）、`phase-16-v9-contract-approval-record.md`（契约）。
